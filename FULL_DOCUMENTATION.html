1. Application Overview

BossMarvs is a personal finance mobile application built with Expo SDK 57 and React Native 0.86. It lets users record income and expense transactions, set monthly category budgets, and gain visual financial insights — all stored locally on the device using AsyncStorage (no cloud, no account required).

🏠 Dashboard

Shows total balance, income/expense pills, a spending plan progress bar, and the 5 most recent transactions.

➕ Add Transaction

Full-screen modal (stack route) where users choose expense/income type, enter an amount, select a category, and save.

📋 Transactions

Searchable, filterable, sortable list of all records. Supports date presets and income/expense type toggling.

💰 Budgets

Set monthly spending limits per category, see real-time progress bars, and receive color-coded threshold alerts.

📊 Analytics

Cashflow health overview, savings rate, top category, daily average expense, and multi-colored category distribution bar.

No Internet Required. All data lives inside the phone's local storage via @react-native-async-storage/async-storage. The app works fully offline at all times.

How the Pieces Fit Together

Think of the app as three layers stacked on top of each other:

  1. Data Layer — AppContext.tsx holds all transactions, budgets, and categories in React state. It reads/writes to AsyncStorage so data survives app restarts. All screens access this layer through the useApp() hook.
  2. Routing Layer — Expo Router uses the file system inside src/app/ to automatically create routes. The (tabs) folder creates the bottom tab bar. The add.tsx file becomes a stack modal.
  3. Presentation Layer — Screen files (index.tsx, transactions.tsx, etc.) compose reusable components from src/components/ and apply styles from theme.ts.

6. Global State – AppContext

src/context/AppContext.tsx

This is the most important file in the app. It is the single source of truth for all data. Think of it like a central database running inside JavaScript memory, with a bridge to permanent storage on the device.

Why React Context? Without Context, you'd have to pass data as "props" from parent component down to every child — this becomes painful with deeply nested components. Context makes all data accessible anywhere in the tree with one hook: useApp().

6.1 Storage Keys (Lines 7–11)

const STORAGE_KEYS = {
  TRANSACTIONS: '@bossmarvs_v2_transactions',
  BUDGETS:      '@bossmarvs_v2_budgets',
  CATEGORIES:   '@bossmarvs_v2_categories',
};

These are the string keys used to read/write data in AsyncStorage (like a dictionary). The _v2_ version prefix ensures that if the data structure changes between app versions, old data won't corrupt the new format — it simply starts fresh.

6.2 Context Creation (Line 13)

const AppContext = createContext<AppContextType | undefined>(undefined);

createContext creates a "broadcast channel" that React components can subscribe to. It's typed with AppContextType | undefined — the undefined default is intentional; it's a safety net to detect when someone uses useApp() outside the Provider.

6.3 State Initialization (Lines 17–20)

const [transactions, setTransactions] = useState<Transaction[]>([]);
const [budgets,      setBudgets]      = useState<Budget[]>([]);
const [categories,   setCategories]  = useState<Category[]>(DEFAULT_CATEGORIES);
const [isLoading,    setIsLoading]   = useState(true);

Four pieces of React state are created with useState:

  • transactions – array of all Transaction records (starts empty, populated from storage)
  • budgets – array of Budget configurations (starts empty)
  • categories – starts with DEFAULT_CATEGORIES immediately so the Add form always has options
  • isLoading – true while reading from storage; prevents screens from rendering stale empty data

6.4 Loading Data from Storage (Lines 23–59)

useEffect(() => {
  async function loadData() {
    try {
      const [storedTx, storedBudgets, storedCats] = await Promise.all([
        AsyncStorage.getItem(STORAGE_KEYS.TRANSACTIONS),
        AsyncStorage.getItem(STORAGE_KEYS.BUDGETS),

Code ConceptExplanation
useEffect(() => {...}, [])The empty [] dependency array means "run this code exactly once, right after the app first mounts" — perfect for initial data loading.
async function loadData()Inner async function defined so we can use await inside a useEffect (useEffect's callback cannot itself be async).
Promise.all([...])Fires all three AsyncStorage reads simultaneously (in parallel) instead of sequentially. This means loading takes the time of the slowest single read, not the sum of all three — significantly faster on startup.
AsyncStorage.getItem(key)Reads a value from storage. Returns null if nothing has been saved yet (first launch). Returns the JSON string if data exists.
JSON.parse(storedTx)AsyncStorage only stores strings. So when saving, we convert objects to JSON strings, and when loading, we parse them back into JavaScript objects/arrays.
finally { setIsLoading(false) }finally runs whether the try succeeded OR an error occurred. This guarantees isLoading always becomes false so the UI never gets stuck on a loading screen.

6.5 addTransaction (Lines 61–70)

const addTransaction = async (txData: Omit<Transaction, 'id' | 'createdAt'>) => {
  const newTx: Transaction = {
    ...txData,
    id: `tx-${Date.now()}-${Math.floor(Math.random() * 1000)}`,
    createdAt: Date.now(),
  };
  const updated = [newTx, ...transactions];
  setTransactions(updated);
  await AsyncStorage.setItem(STORAGE_KEYS.TRANSACTIONS, JSON.stringify(updated));
};
LineExplanation
Omit<Transaction, 'id' | 'createdAt'>The caller only needs to pass the fields the user fills in. The system auto-generates id and createdAt.
...txDataSpread operator — copies all properties from the input into the new object.
id: `tx-${Date.now()}-${Math.random()...}`Creates a unique ID by combining the current Unix timestamp (milliseconds) with a random 3-digit number. The chance of collision is essentially zero.
createdAt: Date.now()Records the exact moment of creation as a Unix timestamp for precise chronological sorting.
[newTx, ...transactions]Inserts the new transaction at the BEGINNING of the array (newest first), then spreads in all the existing ones.
setTransactions(updated)Updates React state immediately — the UI re-renders instantly with the new record visible.
await AsyncStorage.setItem(...)Persists the entire updated array to storage. JSON.stringify converts the JavaScript array into a string that AsyncStorage can store.

6.6 updateTransaction (Lines 72–76)

const updated = transactions.map((item) => (item.id === tx.id ? tx : item));

The .map() call iterates through every transaction. If the current item's id matches the updated transaction's id, it replaces it with the new version. Otherwise, it returns the original. This is the standard React pattern for immutable state updates — always create a new array instead of mutating the existing one.

6.7 deleteTransaction (Lines 78–82)

const updated = transactions.filter((item) => item.id !== id);

.filter() creates a NEW array containing only items where the ID does NOT match the one being deleted. The original array is untouched.

6.8 setBudget (Lines 84–104)

This function handles both creating a new budget AND updating an existing one for the same category:

const existingIndex = budgets.findIndex((b) => b.category === budgetData.category);
if (existingIndex >= 0) {
  // UPDATE existing budget at that index
  updated[existingIndex] = { ...updated[existingIndex], ...budgetData };
} else {
  // CREATE new budget with generated ID
  const newBudget = { ...budgetData, id: `b-${Date.now()}` };
  updated = [...budgets, newBudget];
}

.findIndex() returns -1 if not found, or the array index if found. So >= 0 means "a budget for this category already exists". If it does, we update it in-place (using spread to merge). If not, we append a brand new one.

6.9 getCategorySpent (Lines 112–116)

const getCategorySpent = (category: string): number => {
  return transactions
    .filter((t) => t.type === 'expense' && t.category.toLowerCase() === category.toLowerCase())
    .reduce((sum, t) => sum + t.amount, 0);
};

Filters all transactions to only expenses matching the given category (case-insensitive), then uses .reduce() to add up all the amounts. reduce starts with sum = 0 and adds each transaction's amount to the running total. The final result is the total spent in that category.

6.10 getSummary (Lines 118–132)

Computes three values from all transactions: total income, total expenses, and net balance (income minus expenses). Uses two separate .filter().reduce() chains — one for income, one for expenses.

6.11 clearAllData (Lines 134–139)

Resets state to empty arrays AND removes both storage keys from AsyncStorage. Note categories are NOT cleared — the user keeps their category list even if they delete all transactions.

6.12 Provider and useApp Hook (Lines 141–169)

export function useApp(): AppContextType {
  const context = useContext(AppContext);
  if (!context) {
    throw new Error('useApp must be used within an AppProvider');
  }
  return context;
}

The useApp() function is what every component calls to access global state. The if (!context) check protects against a developer forgetting to wrap their component in <AppProvider> — they'll get a clear error message instead of a cryptic crash.

10. Data Flow & Storage Lifecycle

10.1 Complete Data Lifecycle

USER ACTION COMPONENT CONTEXT (AppContext) STORAGE (AsyncStorage) ───────────────────────────────────────────────────────────────────────────────────────────────────────────── APP LAUNCH → AppProvider mounts → loadData() runs Promise.all reads 3 keys → AsyncStorage.getItem(×3) → Reads JSON strings from disk JSON.parse() converts ←─── returns parsed data setState() updates UI ADD TRANSACTION User taps "Add" → router.push('/add') User fills form User taps "Save" → handleSave() validates addTransaction({...}) → generates ID + timestamp [newTx, ...transactions] setTransactions(updated) → UI immediately re-renders AsyncStorage.setItem() → Writes JSON string to disk DELETE TRANSACTION User swipes delete → confirmDelete() alert User confirms → deleteTransaction(id) → .filter() removes item setTransactions(filtered) → UI immediately re-renders AsyncStorage.setItem() → Writes updated JSON SET BUDGET User taps "Set Budget" → BudgetFormModal opens User picks category User enters limit User taps "Save" → handleSave() validates setBudget({...}) → findIndex() checks existing update OR append to array setBudgets(updated) → UI immediately re-renders AsyncStorage.setItem() → Writes JSON string to disk READ DATA (no writes) Any component calls → useApp().getSummary() → .filter().reduce() on state array (no storage read) Any component calls → useApp().getCategorySpent() → .filter().reduce() on state array (no storage read)
Optimistic Updates: The UI updates immediately (via setState) BEFORE the AsyncStorage write completes. Users see changes instantly, and storage writes happen in the background. This makes the app feel snappy even on slower devices.

10.2 Why This Pattern (Context + AsyncStorage)

✅ No network required

100% local. The app works on airplane mode. No API keys, no server, no monthly fees.

✅ Instant UI response

React state updates synchronously — the UI re-renders before storage writes. Zero perceived delay.

✅ Data persists restarts

AsyncStorage survives closing the app. Data remains until the user clears it or uninstalls.

✅ One source of truth

All components read from the same Context state — no possibility of screens showing inconsistent data.

10.3 Storage Key Design

The app uses three separate storage keys — one per data type:

'@bossmarvs_v2_transactions'   // Array<Transaction>
'@bossmarvs_v2_budgets'        // Array<Budget>
'@bossmarvs_v2_categories'     // Array<Category>

The v2 version prefix is important: if the Transaction interface changes in a future version (e.g., adding a new required field), old data stored with the old key won't break the app — the new version simply starts fresh with a clean slate while the old data sits unused with the old key.
